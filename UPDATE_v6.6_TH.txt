MCI v6.6 — เฉพาะไฟล์ที่แก้ไข/เพิ่ม

วิธีอัปเดตบน GitHub Pages
1. จบรอบที่กำลังเล่น และให้ทุกคนปิดแท็บ/PWA เดิมก่อนอัปเดต
2. แตก ZIP นี้ แล้ววางไฟล์และโฟลเดอร์ข้างในที่ระดับเดียวกับ index.html เดิม
3. แทนที่ index.html และ service-worker.js เพิ่ม mci-client.js, asset-manifest.json และโฟลเดอร์ assets-v66
4. ใช้ icons/ และ manifest.webmanifest เดิมได้ ไม่ต้องอัปโหลดใหม่ และไม่จำเป็นต้องลบ assets/ เดิม
5. รอ GitHub Pages อัปเดต จากนั้นเปิดเว็บใหม่ทุกเครื่อง ห้ามใช้หน้า v6.5 ค้างร่วมกับ v6.6
6. เข้า GM ก่อนหนึ่งครั้ง ระบบจะเติม Supply ตามชุดด้านล่างให้อัตโนมัติในขั้นอัปเดตข้อมูล โดยไม่ต้อง Reset
   หากอัปเดตหน้าแล้วไฟล์ยังเป็นรุ่นเก่า ให้ปิดทุกแท็บและ PWA ของเกม เปิดใหม่ แล้วรีเฟรช

ยังใช้ Firebase config และตำแหน่งฐานข้อมูลเดิม ไม่ต้องสร้าง Firebase ใหม่
ไฟล์นี้ยังไม่ได้ถูกนำขึ้นเว็บจริง และไม่มีการแก้ Firebase จริงจากการทดสอบ

สิ่งที่แก้
- เปลี่ยนการสร้างหน้าหลักใหม่ทั้งก้อนเป็นการแก้ DOM ที่เกี่ยวข้อง เพื่อรักษาฉาก ช่องกรอก และเมนู
- ตำแหน่งผู้เล่นรับทีละรายการ และส่งให้ฉากเป็นข้อความแยกจากข้อมูลผู้ป่วย
- เติมการส่งพิกัดระหว่างเดินใน Hospital/Field และใช้ interpolation สำหรับผู้เล่นคนอื่น
- ให้เครื่องหนึ่งรับหน้าที่อัปเดตเหตุการณ์ตามเวลา พร้อมสิทธิ์ที่หมดอายุและรับช่วงต่อได้
- ย้าย heartbeat ออกจาก roster เพื่อลดการเขียนทับหมวดรายชื่อทั้งก้อน
- อ่านข้อมูลล้มเหลวจะไม่แทนข้อมูลเดิมด้วยค่าเริ่มต้น; ไม่แสดงผล speculative transaction เป็นข้อมูลที่ยืนยันแล้ว
- แก้ read-modify-write ของโรงพยาบาลเป็น transaction และรวมการแก้ setting ที่ต่างช่องกัน
- คงคลังเซฟและข้อมูลที่ไม่รู้จักใน root; หยุดเขียนเมื่อโครงสร้างคลังเซฟผิดปกติ
- Supply ในตู้กับ stock ในเต็นท์ใช้ยอดตรงกัน การส่งของ/หยิบของอัปเดตพร้อมกัน
- ใช้อุปกรณ์จากกระเป๋าที่ถือจริง ไม่หักคลังกลางซ้ำเมื่อเริ่ม treatment
- เพิ่มหน้า preload พร้อมเปอร์เซ็นต์และลองใหม่เมื่อภาพโหลดไม่สำเร็จ
- แปลงภาพเป็น WebP ใน assets-v66 และแก้ชื่อไฟล์ฉากภาษาไทย
- Service Worker มีเวอร์ชันใหม่ ไม่บังคับ reload ระหว่างเล่น และล้างเฉพาะ cache ของ MCI

การเติมข้อมูลเดิมทำเพียงครั้งเดียวต่อฐานข้อมูล: ยกระดับจำนวนที่ต่ำกว่าชุดตั้งต้น แต่รักษาจำนวนที่มากกว่าไว้
เก็บยอดก่อน/หลังใน gc.supplyRepair และตั้ง supplyRepairVersion เพื่อไม่เติมซ้ำเมื่อรีเฟรช
หลังใช้ของจนหมด ยอดต้องคงเป็น 0; Reset รอบใหม่จึงคืนตาม baseline ที่ GM กำหนด
Primary/Secondary ไม่มีตู้ตั้งต้นเพิ่ม ผู้เล่นยังหยิบจาก Supply แล้วถือไปตาม flow เดิม

ผลตรวจ
- ผ่านการทดสอบตรรกะ JavaScript ด้วย 12 client จำลองและ transaction แบบตรวจ conflict/retry
- ทดสอบการหยิบชิ้นสุดท้าย, ส่งของเข้าตู้, เพิ่มโรงพยาบาล 24 รายการพร้อมกัน, เพิ่มรถ 12 คันพร้อมกัน
- ทดสอบ setting คนละช่องพร้อมกัน, ผู้ประมวลผลหลักหนึ่งรายและรับช่วง, อ่านล้มเหลวไม่ทับข้อมูล
- ทดสอบ Reset รักษารถและเซฟเดิม และคืน Supply ตาม baseline
- ตรวจ syntax ของโค้ดหลักและโค้ดฉากหลังประกอบแล้ว และตรวจไฟล์ภาพทั้งหมด
- เบราว์เซอร์ทดสอบไม่สามารถเปิด local preview ได้ จึงยังไม่ใช่ผลรับรองบน iPhone/iPad หรือเครือข่ายจริง

ข้อจำกัดที่ยังมี
รุ่นนี้รักษารูปแบบข้อมูลเดิมเพื่ออัปเดตได้โดยไม่ย้ายฐานข้อมูลทั้งระบบ งานที่เปลี่ยนคนไข้ รถ และทรัพยากรพร้อมกัน
ยังใช้ root transaction เพื่อคงความเป็นชุดเดียวกัน ยังไม่ได้แยกเป็นระบบหลายห้อง/catalog/server backend เต็มรูปแบบ
หากมีคลังประวัติ/เซฟจำนวนมาก root transaction ยังมีต้นทุน จึงควรทดสอบจำนวนผู้เล่นจริงก่อนใช้สอน
การกู้ข้อมูลที่เคยถูกลบไปก่อนหน้านี้ต้องอาศัยประวัติ/ถังขยะ/สำรองเดิม การอัปเดตนี้ไม่ได้สร้างข้อมูลที่สูญหายคืนเอง
